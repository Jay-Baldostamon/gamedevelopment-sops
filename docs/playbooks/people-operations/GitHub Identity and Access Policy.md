# 🛡️ GitHub Identity and Access Policy Playbook

## DEFINE

| Field         | Value                                                                                                                                                                                                  |
| ------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Playbook Name | GitHub Identity and Access Policy                                                                                                                                                                      |
| Purpose       | Standardize GitHub account identity and access rules so every team member has a recognizable handle, uses approved company branding conventions, and is onboarded with a company-owned email identity. |
| Owner         | Engineering Leadership                                                                                                                                                                                 |
| Last Updated  | 2026-07-22                                                                                                                                                                                             |
| Review Cycle  | Every 90 days                                                                                                                                                                                          |

## Prerequisites

- [ ] Team member’s legal/professional full name is confirmed
- [ ] Team member’s hiring company is confirmed (`Hurdman Communications`, `Outrank Strategy`, or `Greencheck`)
- [ ] Team member has access to a company email account for the hiring company
- [ ] Team Lead is available to approve handle and grant organization access

## Step-by-Step Checklist

### Phase 1: Define a Recognizable GitHub Handle

1. **Use** a GitHub handle that is easily recognizable from your real name.
2. **Prefer** a handle format based on your first name, surname, or a clear nickname from your legal/professional name.
3. **Avoid** handles that are random, numeric-heavy, anonymous, or unrelated to your name.
4. **Optionally append** a company tag to the handle when available.
5. **Use only** approved company tags: `hurdman`, `outrank`, or `greencheck`.
6. **Prefer** the company tag for the company you applied for or currently belong to.
7. **Follow** naming examples:

| Full Name               | Acceptable Handle Examples   |
| ----------------------- | ---------------------------- |
| Alan Francis Baldelobar | `alanhurdman`, `alanoutrank` |
| Luis Patrick Villaruz   | `patvillaruzhurdman`         |

- [ ] Handle is recognizable from the team member’s name
- [ ] Handle uses an approved company tag when a tag is added
- [ ] Company tag aligns with hiring company when included

**IF the selected handle is not clearly recognizable, THEN revise it before any access request is submitted.**

### Phase 2: Enforce Account Email Identity

1. **Create** a new GitHub account using the company email address when a new account is required.
2. **Use** the hiring company domain for account creation (for example: `alan@hurdman.net` or `alan@outrankstrategy.com`).
3. **Do not use** a personal email for new company GitHub accounts.
4. **Add** the company email to GitHub account settings.
5. **Verify** the company email in GitHub before requesting organization access.

- [ ] New accounts are created with company email only
- [ ] Company email is added to the account
- [ ] Company email verification is complete

**IF an existing account is reused, THEN the company email must still be added and verified before access is granted.**

### Phase 3: Request and Confirm Organization Access

1. **Send** your GitHub handle to your Team Lead through the approved channel.
2. **Request** GitHub organization invitation after handle and email checks are complete.
3. **Accept** the GitHub organization invitation.
4. **Confirm** repository visibility for assigned projects after joining.
5. **Escalate** to the Team Lead if invite or repository access is delayed beyond the expected onboarding window.

- [ ] Team Lead received the handle
- [ ] Organization invitation is accepted
- [ ] Required repositories are visible

## Common Mistakes & Fixes

| Common Mistake                                            | Fix                                                                                        |
| --------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| Handle is not recognizable from the person’s name         | Rename or recreate the account using a clear name-based handle                             |
| Company tag is used but does not match the hiring company | Update handle to the correct company tag where feasible, or document an approved exception |
| New account was created with personal email               | Create or migrate to a company-email-based account before org access is granted            |
| Company email was added but not verified                  | Complete verification immediately, then continue access provisioning                       |
| Team member requested org access before identity checks   | Pause invite flow and complete handle/email compliance checks first                        |

## Success Criteria

- [ ] GitHub handle is clearly recognizable and name-based
- [ ] Optional company tag, if used, is from approved values only
- [ ] Optional company tag aligns to hiring company preference
- [ ] New GitHub accounts are created using company email
- [ ] Company email is added and verified in GitHub
- [ ] Organization invitation is accepted after identity compliance is complete
- [ ] Assigned repositories are accessible
